## Approach

This is a single-package Next.js project that uses **npm** as its package manager. Dependencies are declared in `package.json` and resolved/locked via `package-lock.json`. There is no monorepo tool (no `pnpm-workspace`, `lerna`, `nx.json`, etc.), no vendored dependencies, and no private registry configuration — all packages come from the public npm registry.

## Key Files

- `package.json` — declares runtime dependencies (`next`, `react`, `@prisma/client`, `next-auth`, `zod`, `lucide-react`, `tailwind-merge`, `clsx`, `class-variance-authority`, `nodemailer`, `bcryptjs`, `server-only`, `client-only`) and dev dependencies (`typescript`, `eslint`, `eslint-config-next`, `vitest`, `@playwright/test`, `prisma`, `tailwindcss`, `@tailwindcss/turbopack`, `tsx`, `@types/*`).
- `package-lock.json` — deterministic lockfile generated by npm; used by CI to pin exact transitive versions.
- `.github/workflows/ci.yml` — CI workflow that runs `npm ci` (installing from the lockfile) on Node 22.
- `docker-compose.yml` — defines the Postgres service consumed at runtime but not an npm dependency.

## Versioning Strategy

Dependencies use **caret ranges** (`^x.y.z`) for most packages, allowing minor/patch upgrades within the major version. Notable exceptions:

- `next` is pinned to an exact version: `16.4.2`.
- `react` and `react-dom` are pinned to exact versions: `19.3.0`.
- `eslint-config-next` is pinned to match the Next.js version: `16.4.2`.

This pattern ensures the framework and React peer dependencies stay aligned while allowing other libraries to receive compatible updates.

## Build & Install Conventions

- The `build` script runs `prisma generate && next build`, so the Prisma client is regenerated before every production build.
- The `db:*` scripts (`db:generate`, `db:migrate`, `db:deploy`, `db:studio`, `db:seed`, `db:reset`) wrap Prisma CLI commands.
- `prisma` is listed as a devDependency; `@prisma/client` is a runtime dependency — standard separation of codegen tooling from shipped code.
- `tsx` is a devDependency used to run the Prisma seed file (`prisma/seed.ts`) via the `prisma.seed` field in `package.json`.

## CI Enforcement

The GitHub Actions workflow (`.github/workflows/ci.yml`) enforces:

- Node.js 22 via `actions/setup-node@v4`.
- Deterministic installs via `npm ci` (not `npm install`), which reads `package-lock.json` and fails if it drifts from `package.json`.
- Dependency caching via `cache: npm`.
- A two-stage pipeline: a `quality` job runs typecheck, lint, and unit tests; an `e2e` job depends on it, spins up a Postgres 16 service, applies migrations, seeds data, builds the app, installs Playwright browsers, and runs e2e tests.

## Constraints Observed

- No `.npmrc` or `.yarnrc` files exist, so there is no custom registry, auth token, or mirror configured — all packages resolve from the default npm registry.
- No vendored third-party code under `node_modules`; everything is fetched at install time.
- No workspace/multi-project setup — this is a flat single-package project.
- The lockfile is committed (`package-lock.json` present in the tree), making dependency resolution reproducible across environments.
- Docker Compose is used only for the Postgres service definition, not for bundling or managing JS dependencies.
