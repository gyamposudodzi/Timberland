## System

This Next.js application uses **npm** as its package manager, with a `package.json` manifest and an accompanying `package-lock.json` lockfile (lockfileVersion 3). There is no vendoring of third-party packages — all dependencies are resolved from the public npm registry at install time.

## Key Files

- `package.json` — declares runtime and dev dependencies, plus scripts for build, test, Prisma, and Playwright.
- `package-lock.json` — deterministic lockfile consumed by CI.
- `.github/workflows/ci.yml` — enforces `npm ci` in both the `quality` and `e2e` jobs, pinning Node to version 22 via `actions/setup-node@v4` with `cache: npm`.
- `docker-compose.yml` — defines the Postgres service used by the app; not a dependency manifest but part of the infra-as-code that ships alongside the JS deps.

## Architecture and Conventions

### Dependency categories

Runtime dependencies (`dependencies`) include the Next.js framework, React 19, NextAuth v5 beta, Prisma client, Zod, Tailwind CSS tooling, Lucide icons, bcryptjs, nodemailer, and small utility packages (`client-only`, `server-only`).

Development dependencies (`devDependencies`) cover TypeScript, ESLint, Vitest unit tests, Playwright E2E tests, Prisma CLI, tsx (used as the Prisma seed runner), and Tailwind v4 tooling. The split is clean: nothing marked as production runtime is under `devDependencies` and vice versa.

### Versioning strategy

Most packages use caret (`^`) ranges, allowing minor/patch upgrades within the declared major version. Notable exceptions:

- `next` is pinned to an exact version: `16.4.2`.
- `react` and `react-dom` are pinned to exact versions: `19.3.0`.
- `eslint-config-next` is pinned to match the Next.js version exactly: `16.4.2`.

This pins the core framework stack while leaving ecosystem libraries open to compatible updates.

### Lockfile usage

CI never runs `npm install`; it runs `npm ci` in both jobs, which requires `package-lock.json` to be present and up-to-date and performs a clean install from the lockfile. This makes builds reproducible across environments.

The CI workflow caches the npm cache directory (`cache: npm` in `actions/setup-node@v4`) keyed by the default npm cache path, speeding up repeated runs.

### Scripts as the single entry point

All dependency-related operations go through npm scripts rather than direct CLI invocations:

- `build` runs `prisma generate && next build` — Prisma client generation is a required step before building.
- `db:*` scripts wrap Prisma CLI commands (`generate`, `migrate dev/deploy`, `studio`, `seed`, `reset`).
- `test` / `test:watch` run Vitest; `test:e2e` / `test:e2e:ui` run Playwright.
- `typecheck` runs `tsc --noEmit`.

Prisma's seed command is configured via the `"prisma": { "seed": "tsx prisma/seed.ts" }` field in `package.json`, so `npm run db:seed` delegates to `tsx` without needing a separate script.

### No private registries or vendoring

There is no `.npmrc`, no `package.json` `publishConfig.registry`, no `GOPRIVATE` equivalent, and no vendored `node_modules`. All packages resolve from the public npm registry. Private/authenticated registries are not configured in this repository.

### Infrastructure dependencies

PostgreSQL is provisioned as a Docker Compose service (`postgres:16-alpine`) and also spun up as a GitHub Actions service container in the e2e job. The database schema lives under `prisma/schema.prisma` with migrations under `prisma/migrations/`, managed by the Prisma CLI invoked through the npm scripts above.

## Conventions and Constraints

- Enforced: CI installs dependencies with `npm ci` (`.github/workflows/ci.yml`, lines 26 and 73), which will fail if `package-lock.json` is missing or out of sync with `package.json`.
- Enforced: CI pins Node.js to version 22 via `actions/setup-node@v4` with `node-version: 22`.
- Convention: Runtime vs. development dependencies are separated into `dependencies` and `devDependencies` respectively in `package.json`.
- Convention: The Next.js and `eslint-config-next` versions are pinned to the same exact version (`16.4.2`) to avoid peer-dependency mismatches.
- Convention: `react` and `react-dom` are pinned to exact versions (`19.3.0`) rather than using caret ranges like most other packages.
- Convention: Prisma operations are always invoked through npm scripts (`db:generate`, `db:migrate`, `db:deploy`, `db:seed`, `db:reset`) rather than directly calling `prisma` on PATH.
- Not observed: No private npm registry configuration, no `.npmrc`, no scoped private packages, and no vendoring strategy.
