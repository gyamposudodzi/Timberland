Two parallel action/service pairs with a strict separation of concerns:
- `account.*` (customer-facing): `account.actions.ts` exposes Next.js Server Actions (`saveAddressAction`, `deleteAddressAction`) that validate via Zod (`addressSchema`), enforce ownership by scoping Prisma queries to `session.user.id`, and call `revalidatePath` on `/account/*`. `account.service.ts` is a pure data layer (`listMyShipments`, `getMyShipmentSummary`, `getMyShipment`, `getSavedAddresses`) that performs Prisma reads/writes scoped to `userId` — no auth logic lives here.
- `admin.*` (admin-only): `admin.actions.ts` exposes privileged Server Actions (`forceShipmentStatusAction`, `updateShipmentAdminAction`, `deleteShipmentAction`, `setUserRoleAction`) gated by `getAdminSession()` from `admin.service.ts`. `admin.service.ts` centralizes the ADMIN role constant, assignable roles list, admin session gate, and read helpers (`listUsersForAdmin`, `ALL_STATUSES`).

Dependency direction: actions depend on services; services depend only on `@/lib/db` (Prisma) and shared libs (`@/lib/auth`, `@/lib/shipment-status`, `@/lib/zones`, `@/lib/validation`, `@/lib/notifications`). There is no cross-dependency between the account and admin halves. Admin writes use explicit transactions (`prisma.$transaction`) to atomically create a tracking event and update the shipment status, then trigger async notifications and path revalidation.
